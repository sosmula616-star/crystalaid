# CrystalAid: дизайн продукта

Дата: 2026-11-01. Статус: утверждён.

CrystalAid — название продукта. Scope пакетов в коде: `@crystalaid/*`.

## 1. Цель

Публичный Discord-бот и Discord Activity, которые превращают обычную активность на сервере в прогресс: XP, уровни, серии, челленджи, награды, рейтинг и косметику.

**Для кого:** участники и администраторы любых серверов, которые добавили бота сами.

**Успех первого релиза:**
- Сервер добавляет бота и настраивает его без участия разработчика.
- Участник открывает Activity без повторного входа и сразу видит свой прогресс и следующее действие.
- Весь прогресс начисляется только на сервере и не накручивается через клиент.
- Интерфейс работает от 320px до ultrawide и в маленьком окне поверх чата.

**Не входит в первый релиз:** реальные платежи, глобальный профиль и глобальные рейтинги, сезоны, маркетплейс, полноценная admin panel. Настройки сервера из первого релиза ограничены разделом 5.3.

## 2. Подпроекты

Каждый подпроект проходит свой цикл «спецификация → план → реализация». Этот документ задаёт общие решения и подробно описывает подпроект 1.

| # | Подпроект | Результат | Зависит от |
|---|---|---|---|
| 1 | Ядро | Монорепо, база, auth, правила XP, API, worker, тесты | нет |
| 2 | Design system и App Shell | Токены, темы, компоненты, каркас Activity | нет, можно вести параллельно с 1 |
| 3 | Bot | Slash-команды, embeds, запуск Activity, сбор событий | 1 |
| 4 | Игровой цикл | Главная, Активность, Профиль, Рейтинг, Награды, Достижения, realtime | 1, 2, 3 |
| 5 | Экономика и события | Магазин, События, Настройки, финальный multi-agent review | 4 |

## 3. Продуктовая модель

### 3.1 Идентичность и изоляция

- `User` один на весь Discord и определяется автоматически.
- XP, уровень, монеты, серия, инвентарь и достижения принадлежат участию в сервере (`GuildMember`). Прогресс на одном сервере не влияет на другой.

### 3.2 Источники XP

Значения по умолчанию лежат в настройках сервера, поэтому позже их можно менять без правок кода.

| Источник | Правило | Условия |
|---|---|---|
| Голос | 4 XP за каждую подтверждённую минуту | В канале минимум 2 участника-человека, не AFK-канал, канал не исключён, пользователь не заглушил себя. Максимум 480 минут за сутки UTC |
| Сообщения | 10 XP | Одно начисление на минутный интервал на сервере. Боты и исключённые каналы не считаются |
| `/daily` | `50 + 5·min(streak, 30)` XP | Один раз за сутки UTC. Пропущенные сутки сбрасывают серию |
| Челленджи | Награда из определения челленджа | Прогресс считается только из событий бота |

Минутный интервал фиксированный, а не скользящий: два сообщения подряд на границе интервала дадут два начисления. Это принято ради простого ключа идемпотентности и не даёт заметной выгоды при накрутке.

### 3.3 Уровни

`xpToNext(level) = 5·level² + 50·level + 100`, новый участник начинает с уровня 0. Формула находится только в `packages/game-rules`.

### 3.4 Монеты

- Новый уровень: `50 + 10·level` монет.
- `/daily`: `100 + 10·min(streak, 30)` монет.
- Награды и челленджи: сумма из их определения.
- Монеты внутренние, не покупаются за деньги, не передаются между участниками и серверами.

### 3.5 Роль Activity

Сам факт открытого Activity XP не даёт. Клиент может только запросить данные и выполнить действие: забрать награду, купить предмет, изменить настройку. Сервер проверяет каждое действие.

### 3.6 Текст сообщений

Бот не запрашивает привилегированный интент Message Content и не читает текст. Нужны только `Guilds`, `GuildMessages`, `GuildVoiceStates`. Без интента поля содержимого приходят пустыми, но автор, канал и факт сообщения доступны. Цена решения: длину и осмысленность сообщения проверить нельзя, от спама защищает только минутный интервал.

Привилегированный интент также требует заявки при 10 000 пользователей и ежегодного продления (правило Discord от 10 июня 2026 года), поэтому отказ от него убирает этот риск для роста.

### 3.7 Роли

`USER`, `MODERATOR`, `ADMIN`, `OWNER` вычисляются на backend из прав Discord: `OWNER` — владелец сервера, `ADMIN` — право Administrator или Manage Guild, `MODERATOR` — Moderate Members. Результат кэшируется на 5 минут. Проверки живут в одном модуле, интерфейс только скрывает недоступное.

## 4. Архитектура

Выбран модульный монолит в TypeScript-монорепо на pnpm workspaces.

```text
Discord Gateway → bot → Redis Stream → worker → PostgreSQL
Slash-команды   → bot → API ────────────────────┘    ↑
Activity (React) → прокси Discord → API / WebSocket ─┘
```

```text
apps/activity        React + Vite, Embedded App SDK
apps/api             Fastify; роли запуска api и worker
apps/bot             discord.js, без доступа к базе
packages/database    схема Drizzle, миграции, клиент
packages/contracts   схемы Zod и типы запросов, ответов, событий
packages/game-rules  XP, уровни, серии, награды: чистые функции
packages/design-system токены, темы, компоненты
packages/i18n        словари ru и en
packages/config      проверка env, общие настройки TS и lint
docs/                документация из master prompt
```

Пакеты `types`, `discord`, `utils`, `ui` из исходного предложения не созданы отдельно: типы живут в `contracts`, компоненты в `design-system`, а общий код добавляется только при реальной необходимости.

**Границы:**
- `bot` превращает события Discord в типизированные события и отправляет их в Redis Stream. На slash-команды отвечает через внутренний API с сервисным токеном. Базы не касается.
- `worker` читает очередь через consumer group и раз в минуту начисляет XP открытым голосовым сессиям.
- `api` и `worker` используют один сервисный слой, поэтому правила существуют в одном месте.

**Перезапуск бота.** После подключения к Gateway бот присылает снимок голосовых каналов. Worker сверяет его с открытыми сессиями и закрывает те, которых больше нет. Минуты, для которых не было подтверждённого состояния, не начисляются.

**Сбои.**
- Redis недоступен: API работает на чтение, realtime отключён, бот буферизует до 10 000 событий в памяти и отбрасывает самые старые сверх лимита. В Redis включён AOF.
- Падение бота: события за время простоя теряются. Это принято, потому что XP не деньги, а снимок восстановит текущие сессии.

## 5. Подпроект 1: ядро

### 5.1 Авторизация Activity

1. Activity вызывает `authorize` с областями `identify` и `guilds` и передаёт `code` и `instanceId` в `POST /auth/activity`.
2. API обменивает код на токен с помощью client secret и получает пользователя через Discord API.
3. API запрашивает `GET /applications/{app}/activity-instances/{instanceId}` с токеном бота и проверяет, что экземпляр существует, у него есть `guild_id`, а пользователь есть в `users`.
4. API создаёт или обновляет `User`, `Guild`, `GuildMember`.
5. API выдаёт JWT сроком 15 минут с `userId` и `guildId`, а также токен доступа Discord для вызова `authenticate` в SDK. JWT хранится только в памяти, потому что cookies внутри iframe ненадёжны.
6. Обновление сессии: клиент повторяет шаги 1–5 без показа окна авторизации (`prompt: "none"`).

`guildId`, присланный клиентом, никогда не используется. Запуск в личных сообщениях (`kind: "pc"`, нет `guild_id`) возвращает `GUILD_REQUIRED`, а Activity объясняет, что нужно открыть его на сервере. Если бот не добавлен на сервер, возвращается `BOT_NOT_INSTALLED` со ссылкой на добавление.

### 5.2 Схема данных

Все таблицы прогресса содержат `guild_id`.

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `users` | Профиль Discord | unique `discord_id` |
| `guilds` | Сервер и `settings` (JSONB) | unique `discord_guild_id` |
| `guild_members` | Участие: `xp`, `level`, `coins`, `streak`, `last_daily_on`, `roles` | unique `(guild_id, user_id)`, index `(guild_id, xp DESC)` |
| `xp_ledger` | Неизменяемый журнал XP | unique `idempotency_key`, index `(guild_id, user_id, created_at)` |
| `coin_ledger` | Неизменяемый журнал монет (Transaction) | unique `idempotency_key` |
| `member_xp_daily` | XP по дням для рейтингов | PK `(guild_id, user_id, day)`, index `(guild_id, day, xp DESC)` |
| `activities` | Сессии и события для истории | index `(guild_id, user_id, created_at)` |
| `voice_sessions` | Открытые и закрытые голосовые сессии | partial unique `(guild_id, user_id)` где `ended_at IS NULL` |
| `achievements` | Каталог достижений | unique `key` |
| `user_achievements` | Полученные достижения | PK `(guild_id, user_id, achievement_id)` |
| `rewards` | Награды, которые можно забрать | unique `key` |
| `reward_claims` | Полученные награды | unique `idempotency_key` |
| `shop_items` | Товары, включая темы | unique `key` |
| `inventory` | Предметы участника | PK `(guild_id, user_id, item_id)` |
| `events` | События сервера | index `(guild_id, start_at, end_at)` |
| `flags` | Подозрительная активность для модераторов | index `(guild_id, status)` |

Отличия от минимальной модели: `Level` входит в `guild_members`, потому что уровень зависит от сервера; `Reward` разделён на `rewards` и `shop_items`, потому что цена есть только у товара; журналы и `flags` добавлены ради аудита и защиты от накрутки.

Ключи идемпотентности:

```text
voice:{guild}:{user}:{yyyyMMddHHmm}
msg:{guild}:{user}:{yyyyMMddHHmm}
daily:{guild}:{user}:{yyyyMMdd}
reward:{guild}:{user}:{rewardKey}:{period}
buy:{guild}:{user}:{itemKey}
```

**Начисление** — одна транзакция: вставка в журнал с `ON CONFLICT DO NOTHING`, при успешной вставке обновление `guild_members` и `member_xp_daily` через `FOR UPDATE` строки участника. `level` и `xp` — производные от журнала, которые можно пересчитать.

**Покупка** — та же транзакция: проверка баланса под блокировкой, запись в `coin_ledger` и `inventory`. Отрицательный баланс запрещён ограничением `CHECK (coins >= 0)`.

**Хранение.** Данные сервера удаляются через 30 дней после удаления бота. Пользователь может удалить свой профиль, журналы при этом обезличиваются.

### 5.3 API

Все ответы проходят схемы из `contracts`. Ошибки имеют единый формат:

```json
{ "error": { "code": "COOLDOWN_ACTIVE", "message": "…", "requestId": "…" } }
```

| Метод | Путь | Доступ |
|---|---|---|
| POST | `/auth/activity` | публичный, лимит запросов |
| GET | `/me` | участник |
| GET | `/leaderboard?period=daily\|weekly\|monthly\|all&cursor=` | участник |
| POST | `/daily` | участник |
| GET | `/rewards`, POST `/rewards/:key/claim` | участник |
| GET | `/achievements` | участник |
| GET | `/shop`, POST `/shop/:key/purchase` | участник |
| GET, PATCH | `/guild/settings` | `ADMIN` и выше |
| GET | `/health` | публичный |
| POST | `/internal/*` | сервисный токен бота |

Настройки сервера первого релиза: AFK-канал, каналы без XP, канал объявлений, значения XP из 3.2 в пределах лимитов.

Лимиты: `/auth/activity` — 10 запросов в минуту на IP, изменяющие запросы — 30 в минуту на пользователя, чтение — 120 в минуту на пользователя. Запросы с клиента проходят через прокси Discord, поэтому IP берётся из заголовка, который выставляет доверенный прокси, а не из произвольного заголовка клиента.

### 5.4 Защита от накрутки

- Прогресс создают только события бота, клиент не передаёт XP, время и суммы.
- Двойной клик и повторная доставка события отсекаются уникальным ключом.
- Подозрительные паттерны записываются в `flags` и не наказываются автоматически: например, дневной голосовой лимит 7 суток подряд или два аккаунта, которые набирают голосовое время только друг с другом. Решение принимает модератор.

### 5.5 Логи и наблюдаемость

Структурные логи Pino с `requestId` и маскированием секретов. Записываются авторизация, начисления наград, транзакции, изменения прав, флаги. `/health` проверяет PostgreSQL и Redis. Отправка ошибок сосредоточена в одном модуле, поэтому Sentry или аналог можно подключить без правок сервисов.

### 5.6 Тесты

- **Unit (Vitest):** `game-rules`, права, идемпотентность ключей.
- **Integration:** API и worker на настоящих PostgreSQL и Redis, Discord замокан на уровне HTTP.
- **Сценарии гонок:** параллельные `/daily` и покупки дают одно начисление или одно списание.

## 6. Design system

### 6.1 Темы

Компоненты используют только семантические токены. Тема — набор их значений, поэтому новая тема не требует правок компонентов.

| Тема | Цена | background | surface | surface-elevated | foreground | muted | primary | on-primary |
|---|---|---|---|---|---|---|---|---|
| Кристалл (фирменная) | бесплатно | `#0B1220` | `#111A2C` | `#18233A` | `#EAF1FA` | `#9AACC6` | `#6FD3F7` | `#06263A` |
| Индиго | 1 500 | `#12131F` | `#191A2B` | `#212338` | `#ECEDF8` | `#9EA1C0` | `#8E8CFF` | `#10102C` |
| Янтарь | 1 500 | `#171412` | `#1F1B18` | `#28231F` | `#F3EEE9` | `#AEA399` | `#F2B04A` | `#2B1A00` |
| Изумруд | 2 500 | `#0F1614` | `#151F1C` | `#1C2925` | `#E8F2EE` | `#93A8A0` | `#3FD9A4` | `#04291D` |
| Графит | 2 500 | `#121416` | `#181B1E` | `#1F2327` | `#EDF0F2` | `#99A2AA` | `#C6F24E` | `#1A2200` |
| Малина | 5 000 | `#1A1216` | `#23191E` | `#2D2127` | `#F6EAF0` | `#B59DA9` | `#F2618F` | `#34061A` |

Тема Кристалл построена на цветах логотипа и заменила Океан: у них почти одинаковый акцент.

Проверено 2026-11-01 расчётом WCAG: все пары текста на фоне, включая `muted` на `surface-elevated` и `on-primary` на `primary`, дают контраст не ниже 5,07:1 при пороге AA 4,5:1. Состояния hover, focus и disabled проверяются в подпроекте 2.

Тема покупается лично, действует на сервере покупки и видна только покупателю. Цены — стартовые значения. Только на `/daily` с непрерывной серией самая дешёвая тема копится примерно 10 дней, монеты за уровни сокращают этот срок.

Цвета статусов и редкости общие для всех тем:

| Редкость | Цвет | Минимальный контраст на `surface-elevated` |
|---|---|---|
| Обычный | `#A3ABB3` | 6,48:1 |
| Редкий | `#5AA9F5` | 6,05:1 |
| Эпический | `#B08CFF` | 5,77:1 |
| Легендарный | `#F5C451` | 9,26:1 |

Статус и редкость никогда не передаются только цветом: всегда есть иконка или подпись. Это особенно важно в теме Янтарь, где акцент похож на предупреждение.

### 6.2 Масштаб

- Отступы: 4, 8, 12, 16, 20, 24, 32, 40, 48, 64, 80.
- Радиусы: 4, 6, 8, 10, 12, 16, 20.
- Шрифт: Inter с кириллицей, начертание tabular для чисел XP и рейтинга.
- Типографика: Display, Heading, Subheading, Body, Label, Caption, Mono; крупные размеры через `clamp()`.
- Анимация: 120–240 мс, заметный акцент только на повышении уровня и получении награды, `prefers-reduced-motion` соблюдается.

## 7. UX

**Навигация.** Раскладка зависит от ширины контейнера (container queries), а не от типа устройства.

| Режим | Когда | Раскладка |
|---|---|---|
| Компактный | Окно поверх чата (`ACTIVITY_LAYOUT_MODE_UPDATE`) или ширина менее 320px | Уровень, XP, одно главное действие |
| Узкий | Контейнер до 720px | Нижняя панель: Главная, Активность, Рейтинг, Награды, Ещё. Остальное в drawer |
| Средний | 720–1279px | Левая панель иконками, контент |
| Широкий | От 1280px | Левая панель с подписями, контент, панель контекста |
| Очень широкий | От 1920px | То же, контент ограничен по ширине, лишнее пространство отдаётся панели контекста |

Значения 720, 1280 и 1920 проверяются в подпроекте 2 на реальном контенте и могут сдвигаться.

**Главный экран отвечает на вопрос «что сделать дальше?».** Над остальным стоит одно действие в порядке приоритета: забрать награду, продолжить серию через `/daily`, выполнить текущий челлендж.

**Первый запуск.**
- Новый участник видит три способа заработать XP вместо пустых нулей.
- Администратор нового сервера проходит короткую настройку: AFK-канал, каналы без XP, канал объявлений.
- Если бот не добавлен, Activity объясняет это и предлагает добавить его.

**Состояния.** Каждая асинхронная страница имеет loading, empty, error с Retry и success. Ошибка одного блока не ломает страницу благодаря error boundaries.

**Язык.** Все тексты идут через `packages/i18n` на русском и английском. Язык определяется по локали Discord, изменить его можно в настройках.

## 8. Требования к окружению

На машине разработки сейчас нет Node.js, pnpm и Docker. Перед реализацией нужны:
- Node.js текущей LTS-версии и pnpm.
- PostgreSQL и Redis: локально через Docker или в облаке.
- Приложение в Discord Developer Portal и его ключи в локальном `.env`. Настоящий запуск внутри Discord проверяется вручную с участием владельца приложения.

## 9. Критерий готовности подпроекта 1

- Монорепо собирается, typecheck, lint и все тесты проходят.
- Миграции создают схему раздела 5.2 на чистой базе.
- `/auth/activity` отклоняет запрос без действующего экземпляра Activity и запрос пользователя, которого нет в экземпляре.
- Тестовые события бота приводят к начислению XP, повышению уровня и появлению в рейтинге.
- Повторные и параллельные запросы не приводят к двойному начислению или списанию.
- `.env.example` есть, секреты не попадают в клиентскую сборку и логи.
