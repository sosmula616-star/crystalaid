# CrystalAid: система учёта ветки стаффа

Дата: 2026-11-01. Статус: утверждён. Заменяет игровую версию спецификации.

## 1. Цель

CrystalAid — приватный Discord-бот и Discord Activity для одной ветки стаффа на сервере. Он ведёт тикеты, учитывает онлайн и смены, контролирует нормы, хранит кадровые данные, начисляет зарплату в токенах и даёт тратить их во встроенном магазине.

**Пользователи:** саппорты, кураторы, администраторы. Обычные участники сервера только создают тикеты и оценивают их.

**Успех первого релиза:**
- Новый саппорт появляется в составе автоматически после выдачи роли.
- Руководство видит, кто сколько работал и выполнил ли норму, без ручных таблиц.
- Каждая операция с токенами и кадрами объяснима: кто, кому, что и почему.
- Администратор сам настраивает доступы, ставки, нормы и магазин без правок кода.

**Не входит в первый релиз:** XP, уровни, достижения, публичная установка на другие серверы, реальные платежи, учёт банов и мутов, отдельный сайт вне Discord.

## 3. Роли и доступы

### 3.1 Конфиг

Настройки сервера лежат в `crystalaid.config.json` в корне. Файл не коммитится, образец — `crystalaid.config.example.json`. Секретов в нём нет.

```json
{
  "guildId": "",
  "timezone": "Europe/Moscow",
  "roles": { "support": [""], "curator": [""], "admin": [""] },
  "channels": { "ticketCategory": "", "ticketPanel": "", "reports": "", "audit": "" }
}
```

Файл проверяется схемой при запуске. При ошибке процесс не стартует и называет неверное поле.

### 3.2 Уровни

Уровень вычисляется на backend только из текущих ролей Discord, берётся самый высокий подходящий.

| Уровень | Условие |
|---|---|
| `ADMIN` | Есть роль из `roles.admin` |
| `CURATOR` | Есть роль из `roles.curator` **и** роль из `roles.support` |
| `SUPPORT` | Есть роль из `roles.support` |
| `NONE` | Остальные, доступа к панелям нет |

Человек только с ролью куратора без роли саппорта получает `NONE`, панель объясняет причину.

**Синхронизация.** Бот слушает `GUILD_MEMBER_UPDATE` и при запуске полностью сверяет состав. Появление роли создаёт запись в составе. Потеря всех ролей ветки переводит запись в статус `inactive`: доступ закрывается сразу, история и баланс сохраняются. Возврат роли восстанавливает запись.

### 3.3 Настраиваемые права

Права задаются для уровней `SUPPORT` и `CURATOR` в админ-панели. `ADMIN` имеет все права всегда, это защита от случайной потери доступа.

| Право | По умолчанию |
|---|---|
| `tickets.view_all` | CURATOR |
| `tickets.read_transcript` | CURATOR |
| `tickets.transfer` | CURATOR |
| `shifts.edit` | CURATOR |
| `absences.approve` | CURATOR |
| `staff.warn` | CURATOR |
| `staff.note` | CURATOR |
| `reports.view` | CURATOR |
| `payroll.approve` | только ADMIN |
| `tokens.grant` | только ADMIN |
| `tokens.deduct` | только ADMIN |
| `shop.manage` | только ADMIN |

Для `tokens.grant` и `tokens.deduct` можно задать лимит суммы на операцию. Причина обязательна всегда. Сотрудник не может менять собственный баланс, смены и выговоры, даже если у него есть право. Для `ADMIN` это правило тоже действует.

Права проверяются на backend при каждом запросе и читаются из базы, а не из токена сессии.

## 4. Функции

### 4.1 Тикеты

1. Бот публикует в `channels.ticketPanel` сообщение с кнопкой и категориями, заданными админом.
2. Участник выбирает категорию и кратко описывает проблему. Бот создаёт приватный канал в `channels.ticketCategory`. На пользователя и категорию — один открытый тикет.
3. Саппорт нажимает «Взять». Тикет закрепляется за ним.
4. Саппорт закрывает тикет с указанием результата. Канал удаляется, переписка сохраняется в базе.
5. Бот отправляет пользователю в личные сообщения оценку от 1 до 5. Если личные сообщения закрыты, оценки нет.

Метрики: количество взятых и закрытых тикетов, время до первого ответа, время решения, средняя оценка. Первый ответ — первое сообщение сотрудника ветки после создания тикета.

Статусы: `open`, `claimed`, `closed`. Передача тикета записывается в историю. Текст переписки хранится 90 дней, метрики — бессрочно. Тикет без ответа 30 минут вызывает уведомление кураторам, значение настраивается.

### 4.2 Онлайн и голос

Считается только для состава со статусом `active`. Данные агрегируются по дням.
- **Время в сети:** статус Discord не `offline`.
- **Время в голосе:** в голосовом канале не AFK. Пользователь с отключённым звуком не считается.
- **Сообщения:** количество, без текста.

Вне каналов тикетов текст сообщений не сохраняется.

### 4.3 Смены и нормы

- Смена начинается и завершается кнопкой или `/shift`. Открытая смена может быть только одна.
- Нет активности 30 минут (сообщения, голос, действия с тикетами): бот спрашивает, на месте ли сотрудник. Нет ответа 10 минут: смена закрывается с пометкой `auto_closed`, эти 40 минут в неё не входят. Значения настраиваются.
- Правка смены доступна по `shifts.edit`, с причиной и записью в журнал.
- Норма на неделю: часы смен и закрытые тикеты, задаётся админом.
- Отсутствие: сотрудник подаёт заявку с датами, её подтверждает обладатель `absences.approve`. Норма снижается пропорционально подтверждённым дням.

Неделя начинается в понедельник 00:00 по `timezone` из конфига.

### 4.4 Кадры и отчёты

- Карточка сотрудника: должность, дата прихода, статус, активные выговоры, заметки, история изменений.
- Заметки видят только обладатели `staff.note`.
- Выговор содержит причину, автора и срок действия, по умолчанию 30 дней. Снять его досрочно можно с причиной.
- Еженедельный отчёт: в понедельник бот публикует в `channels.reports` итоги недели, а полная таблица доступна в панели. В публичном канале не показываются заметки и выговоры.

### 4.5 Зарплата

Ставки задаёт админ:

| Параметр | По умолчанию |
|---|---|
| Токены за закрытый тикет | 10 |
| Токены за час смены | 5 |
| Бонус за выполненную норму | 50 |

1. В понедельник бот создаёт черновик ведомости за прошлую неделю: строка на каждого сотрудника с расчётом.
2. Обладатель `payroll.approve` проверяет строки, может скорректировать сумму с причиной.
3. Утверждение начисляет токены одной транзакцией и сообщает сотрудникам результат. Повторное утверждение невозможно.

Отсутствие снижает норму, а не ставку. Выговоры не меняют сумму автоматически.

### 4.6 Магазин

Админ создаёт товары: название, описание, цена, остаток (пусто — без ограничения), активность и тип выдачи.

| Тип | Выдача |
|---|---|
| `role` | Бот сразу выдаёт указанную роль |
| `theme` | Открывает тему оформления |
| `manual` | Создаёт заявку, админ подтверждает или отклоняет с возвратом токенов |

Покупка, отказ и возврат проходят через журнал токенов. Если бот не смог выдать роль, заказ переходит в `failed`, токены возвращаются автоматически.

### 4.7 Токены

Баланс не может быть отрицательным. Журнал `token_ledger` неизменяем, исправление — только новая операция. Типы: `payroll`, `grant`, `deduct`, `purchase`, `refund`.

## 5. Интерфейс

Панели находятся внутри Activity и используют одну дизайн-систему.

| Уровень | Разделы |
|---|---|
| Саппорт | Обзор, Смена, Тикеты, Статистика, Магазин, Настройки |
| Куратор | + Состав, Смены состава, Все тикеты, Отчёты |
| Админ | + Роли и доступы, Зарплата, Нормы, Магазин (управление), Журнал |

Обзор отвечает на вопрос «что сделать дальше?»: открыть смену, взять ждущий тикет, посмотреть прогресс нормы.

Навигация, адаптивность, компактный режим окна поверх чата и состояния страниц — как определено в master prompt: раскладка по ширине контейнера, нижняя панель на узком экране, loading, empty, error с Retry, success.

Команды: `/shift`, `/profile`, `/balance`, `/ticket panel`, `/help`. Панель открывается из Discord через запуск Activity.

Тексты идут через i18n, русский основной, английский добавляется без правок компонентов.

## 6. Архитектура

Модульный монолит в TypeScript-монорепо на pnpm workspaces.

```text
Discord Gateway → bot → Redis Stream → worker → PostgreSQL
Команды, кнопки → bot → API ─────────────────────┘    ↑
Activity (React) → прокси Discord → API / WebSocket ──┘
```

```text
apps/activity        React + Vite, Embedded App SDK
apps/api             Fastify; роли запуска api и worker
apps/bot             discord.js, без доступа к базе
packages/database    схема Drizzle, миграции, клиент
packages/contracts   схемы Zod и типы
packages/domain      правила ролей, смен, норм, зарплаты: чистые функции
packages/design-system токены, темы, компоненты
packages/i18n        словари
packages/config      env и конфиг сервера (готово)
```

**Интенты Discord:** `Guilds`, `GuildVoiceStates`, `GuildMessages`, а также привилегированные `GuildMembers`, `GuildPresences`, `MessageContent`. Заявка в Discord нужна начиная с 10 000 пользователей приложения. Содержимое сохраняется только в каналах тикетов.

**Авторизация Activity:**
1. Activity передаёт `code` и `instanceId` в `POST /auth/activity`, области `identify` и `guilds`.
2. API обменивает код, проверяет экземпляр через `GET /applications/{app}/activity-instances/{instanceId}` с токеном бота: `guild_id` совпадает с `guildId` из конфига, пользователь есть в `users`.
3. API выдаёт JWT на 15 минут с `userId` и `discordUserId`. Клиент хранит его только в памяти.
4. `NONE` получает `403 NOT_STAFF`, запуск вне сервера — `400 GUILD_REQUIRED`.

**Сбои.** Redis недоступен: API работает на чтение, бот буферизует до 10 000 событий. Бот недоступен: начисление времени останавливается, ключ `bot:alive` со сроком 90 секунд не даёт считать простой; открытые смены не закрываются автоматически, пока бот не вернётся.

**Логи.** Pino с `requestId`, маскирование токенов, client secret, `code`. `/health` проверяет PostgreSQL и Redis.

**Защита.** Лимиты: `/auth/activity` — 10 в минуту на IP, изменения — 30 в минуту на пользователя, чтение — 120 в минуту. Все входы проверяются Zod. Ошибки: `{ "error": { "code", "message", "requestId" } }`.

## 7. Данные

Все таблицы содержат `guild_id`.

| Таблица | Назначение | Ограничения |
|---|---|---|
| `users` | Профиль Discord | unique `discord_id` |
| `staff_members` | Состав: статус, должность, `joined_at`, `token_balance` | unique `(guild_id, user_id)`, `CHECK (token_balance >= 0)` |
| `role_permissions` | Права уровней и лимиты | PK `(guild_id, level, permission)` |
| `settings` | Ставки, нормы, таймауты, категории тикетов (JSONB) | PK `guild_id` |
| `audit_log` | Журнал всех действий | только вставка, index `(guild_id, created_at)` |
| `tickets` | Тикет, статус, метрики, оценка | partial unique `(guild_id, requester_id, category)` при `status <> 'closed'` |
| `ticket_events` | История: взят, передан, закрыт | index `(ticket_id)` |
| `ticket_messages` | Переписка, 90 дней | index `(ticket_id, created_at)` |
| `staff_daily` | По дням: сеть, голос, сообщения, смены, тикеты | PK `(guild_id, user_id, day)` |
| `presence_sessions`, `voice_sessions` | Открытые интервалы | partial unique `(guild_id, user_id)` при `ended_at IS NULL` |
| `shifts` | Смены | partial unique `(guild_id, user_id)` при `ended_at IS NULL` |
| `absences` | Заявки на отсутствие | index `(guild_id, user_id, starts_on)` |
| `warnings`, `staff_notes`, `career_events` | Кадры | index `(guild_id, user_id)` |
| `token_ledger` | Журнал токенов | unique `idempotency_key` |
| `payroll_periods`, `payroll_lines` | Ведомости | unique `(guild_id, week_start)`, unique `(period_id, user_id)` |
| `shop_items`, `shop_orders` | Магазин | index `(guild_id, status)` |

Операции с балансом — одна транзакция: блокировка строки сотрудника, запись в журнал, обновление баланса. Ключи идемпотентности: `payroll:{period}:{user}`, `order:{orderId}`, `refund:{orderId}`, `manual:{requestId}`, где `requestId` создаёт клиент.

## 8. Тестирование

- Unit: уровни и права, расчёт зарплаты, нормы, границы недели и часовые пояса.
- Integration: API и worker на настоящих PostgreSQL и Redis, Discord замокан на уровне HTTP.
- Гонки: двойное утверждение ведомости, параллельные покупки последнего товара, двойное взятие тикета.
- E2E: вход, смена, тикет, ведомость, покупка.

## 10. Окружение и развёртывание

Локально: Node.js 26, pnpm 12, PostgreSQL 18, портативный Redis 5.0.14, поэтому код использует только команды Redis 5. На хостинге нужны постоянно работающие `bot`, `api`, `worker`, PostgreSQL и Redis; Activity — статика. Настоящий запуск в Discord проверяется вручную после создания приложения в Developer Portal.
