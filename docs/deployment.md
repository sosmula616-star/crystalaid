# Развёртывание

Существуют API, worker и Activity (статический клиент, см. последний раздел). Бота пока нет: события в `events:bot` некому присылать.

## Требования

- Node.js и pnpm, `pnpm install --frozen-lockfile`.
- PostgreSQL (проверено на 18).
- Redis 5 или новее. Используются только команды Redis 5 (потоки, `XCLAIM`); `docker-compose.yml` поднимает Redis 7.

## Настройка

1. Переменные окружения (образец: `.env.example`). API и worker при старте читают `.env` из корня репозитория, если файл есть (`apps/api/src/main.ts`, `process.loadEnvFile`). Переменные, заданные в настоящем окружении, сильнее файла, поэтому менеджер процессов может переопределить любую. `pnpm db:migrate` файл `.env` тоже читает. Переменные:

   | Переменная | Смысл |
   |---|---|
   | `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN` | приложение Discord |
   | `DISCORD_API_URL` | по умолчанию `https://discord.com/api/v10` |
   | `DATABASE_URL`, `REDIS_URL` | подключения; в `REDIS_URL` должен быть пароль |
   | `POSTGRES_PASSWORD`, `REDIS_PASSWORD` | пароли для `docker-compose.yml` (только для него; сервисы читают их из URL) |
   | `JWT_SECRET`, `SERVICE_TOKEN` | секреты, не короче 32 символов |
   | `TRUSTED_PROXIES` | адреса или CIDR обратных прокси через запятую; пусто: не доверять никому |
   | `PORT` | порт API, по умолчанию 3001 |
   | `CONFIG_PATH` | путь к файлу конфигурации сервера (необязательно) |

2. Конфигурация сервера: скопировать `crystalaid.config.example.json` в `crystalaid.config.json` в корне репозитория (файл в git не попадает) или указать путь в `CONFIG_PATH`. В нём гильдия, часовой пояс, роли поддержки, куратора и администратора и каналы. Один идентификатор роли не может стоять в двух списках.

3. Миграции: `pnpm db:migrate` (берёт `DATABASE_URL`). `tsx` входит в зависимости пакета `packages/database`, поэтому команда работает и после `pnpm install --prod`.

## Запуск

Сервисы работают прямо из исходников через tsx, без сборки. `pnpm build` собирает Activity и требует `VITE_DISCORD_CLIENT_ID`.

```
pnpm --dir apps/api run api
pnpm --dir apps/api run worker
```

Оба завершаются по SIGTERM и SIGINT. Worker можно запускать в нескольких экземплярах: общая группа Redis делит события между ними. API слушает `0.0.0.0:PORT`. `GET /health` подходит для проверки живости.

## Redis

Redis это граница доверия. Любой, кто может писать в поток `events:bot`, может выдать себе роль администратора: событие `member.updated` с ролью администратора из `crystalaid.config.json` создаёт запись ADMIN, а у администратора есть все права, включая настройки и права ролей. Поэтому в рабочей среде Redis должен быть закрыт от сети и защищён паролем (`requirepass` и пароль в `REDIS_URL`). Не публикуйте порт Redis наружу. `docker-compose.yml` привязывает порты PostgreSQL и Redis к `127.0.0.1`, пароли берёт из `POSTGRES_PASSWORD` и `REDIS_PASSWORD`. Писать в `events:bot` должен только бот. См. [security.md](security.md).

## Обратный прокси

- В `TRUSTED_PROXIES` нужно перечислить адреса прокси. Если оставить пусто, API видит адрес прокси вместо адреса клиента, и все клиенты делят один счётчик лимита входа (10 в минуту).
- Порт API не должен быть доступен напрямую, когда есть прокси: в обход прокси пропадают его TLS и фильтрация. Откройте порт только для прокси (файрвол или привязка к внутренней сети). Адрес вне `TRUSTED_PROXIES` не может подменить адрес клиента через `X-Forwarded-For`.
- Прокси завершает TLS; API его не обслуживает.
- Трафик Activity к API приходит через прокси Discord. Его адреса, возможно, нельзя перечислить в `TRUSTED_PROXIES`. Тогда API увидит один и тот же адрес у всех и все входы поделят один счётчик лимита (10 в минуту). Это проверяется при первом запуске (см. список ниже); до тех пор решение не принято.

## Известные ограничения

Перечислены в [security.md](security.md). Из эксплуатационных: события, не обработанные за 5 попыток, лежат в `events:dead` и требуют ручного разбора.

## Activity (статика)

Activity это статические файлы, сервера у неё нет.

1. Задать `VITE_DISCORD_CLIENT_ID` (идентификатор приложения Discord, тот же, что `DISCORD_CLIENT_ID`). Значение вшивается в сборку: его читают при сборке из корневого `.env` или из окружения, после сборки сменить нельзя. Если значение пусто, `vite build` завершается ошибкой с пояснением (режим `mock` не собирается в продакшен). Из `.env` в клиент попадают только переменные с префиксом `VITE_`; секреты (`DISCORD_CLIENT_SECRET`, `JWT_SECRET`) туда не попадают.
2. Собрать: `pnpm --dir apps/activity run build` (проверка типов и `vite build`). Результат в `apps/activity/dist`: `index.html` и `assets/`. Шрифт и значки лежат внутри, внешних запросов нет, кроме доменов Discord из SDK (в файлах есть ещё строки библиотек: `www.w3.org`, `json-schema.org`, `react.dev`, `github.com`, `localhost`, они не запрашиваются).
3. Разместить `dist` на любом статическом хостинге с HTTPS. Для кэша хватит значения по умолчанию: имена файлов в `assets/` содержат хэш, `index.html` кэшировать не нужно.
4. В портале разработчиков Discord, раздел Activities, URL Mappings:

   | Префикс | Цель |
   |---|---|
   | `/` | адрес статического хостинга без `https://` |
   | `/api` | адрес API (прокси перед `apps/api`) |

   Activity обращается к `/api/...`, Discord передаёт запрос по цели без префикса `/api`, поэтому у API нет префикса в маршрутах (`/me`, `/auth/activity`). Тот же адрес работает в разработке: `vite` проксирует `/api` на `127.0.0.1:3001`.
5. Подставной режим и витрина `/kit` в сборку не входят; это проверяет `pnpm --dir apps/activity run test:e2e` (`bundle.spec.ts`).

### Первый запуск в Discord

Проверить по порядку, на настоящем сервере. Локально это не воспроизводится.

1. Адрес API: установленный SDK 2.5.0 не обрабатывает `.proxy` сам. В первом настоящем запуске проверить в сетевой вкладке, что запросы доходят до API через URL Mapping (`/api/...`, API получает `/auth/activity`). Если Discord требует префикс `/.proxy`, изменить `baseUrl` в клиенте API.
2. Настоящая CSP: Discord выдаёт Activity собственную политику, которой на локальном `vite` нет. Открыть Activity в Discord с консолью и убедиться, что нет ошибок CSP: шрифт, изображения и скрипты грузятся только со своего адреса.
3. Окно согласия: при первом входе Discord показывает диалог с запросом `identify` и `guilds`. Нужно прочитать его и принять; на это даётся 5 минут, потом вход заканчивается ошибкой подключения. Повторный вход проходит без диалога.
4. Режим «поверх чата» (PIP) при старте: запустить Activity уже свёрнутой и убедиться, что показывается компактный вид, а после разворота возвращается обычный.
5. `TRUSTED_PROXIES`: сделать несколько входов с разных учётных записей и проверить в журнале API, что адреса клиентов различаются. Если у всех один адрес, входы делят один счётчик лимита (10 в минуту), и адреса прокси Discord нужно добавить в `TRUSTED_PROXIES` или решить вопрос лимита иначе.
